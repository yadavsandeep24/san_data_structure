# Source code — every problem in four languages

The book's code, extracted into real projects you can open in an IDE, build and change. One file per problem (or worked example) per language, generated from the chapters and `solutions/`, and **compile-checked**.

| Language | Project | Files | Build |
|----------|---------|-------|-------|
| Kotlin | [`kotlin/`](kotlin/) — Gradle, JVM | 308 | `gradle compileKotlin` |
| Swift | [`swift/`](swift/) — Swift package | 342 | `swift build` |
| Dart | [`dart/`](dart/) — Dart package | 340 | `dart pub get && dart analyze lib` |
| TypeScript | [`typescript/`](typescript/) — npm package | 311 | `npm install && npm run typecheck` |

Run every language whose toolchain you have installed:

```bash
./src/verify.sh
```

Or a single language:

```bash
./src/verify.sh swift
```

## How the code is organized

- **One namespace per problem**, so the same function name can appear in many problems without clashing:
  - Kotlin: package `chNN.<problem>` (e.g. `ch07.p01_two_sum`) in `kotlin/src/main/kotlin/chNN/`.
  - Swift: one library target per problem (e.g. `Ch07_P01TwoSum`) in `swift/Sources/`, all listed in `Package.swift`.
  - Dart: one library per problem in `dart/lib/chNN/`.
  - TypeScript: one module per problem in `typescript/src/chNN/`.
- **Each file starts with a comment** naming the book section and source file it came from.
- **Shared node types:** `ListNode` and `TreeNode` live in `kotlin/.../common`, `swift/Sources/DSACommon`, `dart/lib/common` and `typescript/src/common`. They accept both `.value` and `.val`, because the book uses both.
- **Usage snippets** that the book shows at top level (for example `pq.add(5)`) are wrapped in `example()` functions, since Kotlin, Swift and Dart don't allow statements outside functions in a library.
- **Problems that build on another section** import it (Kotlin, Dart, TypeScript) or carry a copy of the needed types in a `Shared_*.swift` file (Swift, where each problem is its own module).
- **Small additions for compilation** are marked with a comment, e.g. `// minimal model for this example` where the book refers to a `Post` or `Message` type without defining it, or `…Slow` / `…Buggy` names where a "bad vs good" pair defines the same function twice.

## Platform snippets (not compiled)

A few book snippets only make sense inside a real app (RecyclerView, Fragments, Compose, UIKit, SwiftUI, Flutter widgets). They're kept as plain files for reference but are **not** part of the compiled projects:

- `kotlin/android-snippets/` — need an Android project (AndroidX, Compose)
- `swift/apple-framework-snippets/` — need UIKit / SwiftUI
- `dart/flutter-snippets/` — need Flutter
- `typescript/react-native-snippets/` — need React Native

## Keeping the book and the code in sync

The book stays the place to learn; this folder is the place to run and change code. If you fix a bug in one, fix it in the other. Compiling this folder found several real bugs in the book's snippets (fixed in both places): a missing `kotlin.random.Random` import, `continue` inside a Kotlin lambda, `Duration.seconds` in Swift, assigning `StringBuffer.length` in Dart, and an unchecked `Map.keys().next().value` in TypeScript.
